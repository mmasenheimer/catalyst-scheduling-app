CATalyst Studios – Scheduling App Proposal

Michael Masenheimer

Revised August 2026


==============================================================================
PURPOSE
==============================================================================

Scheduling at CATalyst Studios currently happens in WhenToWork, a software that
helps managers create work calendars, track staff availability, and handle shift
trades or time-off requests through their website. It currently lacks integration
with our workplace hub, Slack.

I'm proposing the CATalyst Scheduling app, which aims to solve any UI, budget, and
Slack integration griefs the managers at the studio have. The UI is (hopefully)
intuitive for managers to visually drag and drop "building blocks" to create
schedules, with alerts set for specific fields like weekly hour limits, desk
coverage, event coverage, and understaffed days.

WhenToWork is a recurring subscription. Through University of Arizona research
funding, I plan to host this application on Jetstream2, which brings the studio's
monthly scheduling cost from $30 down to $0.

The app will also feature full Slack integration via the API, where events and
workflows seamlessly translate into one another, which is yet to be implemented
(in testing stage).

The end result is an easy-to-use app that cuts the fluff out of bigger products
like WhenToWork, and is easily feature-customizable for anything CATalyst related.
Managers have absolute control over the scheduling, and no more annoying emails
from WhenToWork.


Secondary goals the system is built around:

A single roster of records. Adding or removing an employee updates scheduling,
login access, event assignments, and permissions in one action. There's no second
place you have to remember to go update.

Self-service for employees. Availability, drop requests, and coverage/swap requests
flow through the app instead of the manager's inbox.

Reusable structure. Recurring weekly patterns are saved as templates, so building
the weeks out starts from a known-good baseline rather than a blank grid.


==============================================================================
WHERE THE PROJECT STANDS
==============================================================================

Everything described in this document is built and working. The app runs
end-to-end — managers schedule, employees request coverage, notifications fire,
approvals apply changes to the real schedule.

Two things aren't done yet. Slack integration is scaffolded but not connected: the
library is installed and the backend will connect the moment it's given
credentials, but no messages flow yet. And the app hasn't been deployed — it
currently runs locally against a hosted MongoDB Atlas database. Both are covered
at the end under Next Steps.

SET / CHANGE PASSWORD
---------------------

[ IMAGE 3 — The "Forgot your password?" panel ]

This page is obtained via the "Forgot Password?" button on the login page. There's
no email anywhere in this system, on purpose — everything is internal to CATalyst,
so the manager holds the reset. I figured password reset through the manager would
be easier than adding in your email.

The set/change password screen serves 2 purposes:

1. First-time setup (forced). New accounts are created with a temporary password
   and cannot use any part of the application until the employee sets their own.
   The manager handles the temporary passwords on creation of an employee, but
   never sees the password that employee sets themselves.

[ IMAGE 4 — Three panels showing the whole first-run sequence:
  (a) Manage Staff, with "Reset Password" beside each employee
  (b) the one-time temporary password shown to the manager after adding someone
  (c) the "Set your password" screen the employee sees on first sign-in ]

What's shown above: at the top, the manager view can add and remove CATalyst
employees from the app. When the manager adds a new hire, they're given a
temporary password, which is randomly generated and shown exactly once (panel b,
still in the manager view). The employee then logs in with their username and that
temporary password, which drops them straight onto the set-password screen (panel
c). They pick their own password there, and that's what they use from then on.

If a temporary password gets lost before it's used, the manager just issues a new
one with "Reset Password."

2. Voluntary change. Requires the current password, so an unattended logged-in
   browser can't be used to lock the owner out. Changing your password signs out
   your other sessions but keeps the current one.


MANAGER ACCOUNTS
----------------

Manager accounts are provisioned separately from employee accounts, and they're not
part of the schedulable roster — a manager doesn't show up as a row on the schedule
grid. More than one manager can have their own account, and they can all be signed
in at the same time without stepping on each other.

One thing worth knowing if multiple managers use the app: notifications addressed to
"the manager" are a single shared item. If one manager dismisses a pending request,
it disappears for all of them. The request itself is fine and still sitting in the
app waiting to be decided — it's only the reminder that's gone. So the practical
advice for a second or third manager is: read, don't dismiss.

TEMPLATES
---------

[ IMAGE 12 — The templates list, showing the weekly and day sections ]

Templates are a sandbox. Nothing you do inside one touches the live schedule — it's
a place to work out how a week fits together before committing to it. Changes only
reach the real schedule when you explicitly apply the template to a date.

Managers can save work templates in 2 different ways:

    Day templates       a single day's layout, which you can apply to any date

(2), (3), for duplicates.


CREATING A TEMPLATE

Clicking "+ New Template" lets managers create a weekly or day template from
scratch.

Clicking "+ Auto-Generate from Availability" builds an entire week out of what
staff have actually submitted, and saves it as a weekly template. This is the piece
most worth understanding, so it gets a full explanation below.

[ IMAGE 13 — The New Template dialog, and the auto-generate result screen showing
  the proposed week with per-person hours ]


HOW AUTO-GENERATION WORKS

The generator breaks each open day into 30-minute slots and walks through them,
filling any slot that's below its required headcount with the best available
person.

"Best" is decided by a short priority list: strongly prefer whoever is already
working the previous slot, which is what makes continuous shifts emerge instead of
scattered fragments; then whoever can cover a worthwhile stretch; then whoever has
the lowest share of their weekly hour cap, so the work spreads fairly in proportion
to what each person offered.

Nobody is ever scheduled outside their submitted availability, or past their daily,
weekly, or shift-length limits. If no one is available, the slot is left short and
reported as a gap rather than quietly filled.

It runs two passes across the entire week — every day's true minimum first, then a
one-person cushion on top — so padding early days can't starve a later day's
minimum.

A few rules exist specifically because student availability is almost never one
clean block per day:

    - Fragmented availability is handled directly. Somebody available 8–11 and
      then again 2–6:30 because of a class in the middle can be given both blocks
      as two separate shifts, and the generator will do that when the day needs
      the coverage.

    - It won't ask someone back for an unreasonably short second shift. If a
      person already worked that day and isn't continuing straight through, a
      second block only gets offered if it meets the full minimum shift length.
      Nobody's getting asked to come back to campus for half an hour.

Desk coverage gets assigned in the same run:

    - Desk turns are only placed during the hours the desk actually needs to be
      staffed: 9:00–6:00 Monday through Thursday, 9:00–5:45 Friday, and
      1:00–6:00 Sunday
    - A single desk turn is capped at one hour
    - The generator tries to avoid giving any one person two desk turns inside
      the same shift

Finally, consecutive slots are merged into shifts, anything under two hours is
stretched into adjacent availability where limits allow, and the result comes back
with per-person hours, warnings, and any coverage gaps for review before you save
it.

----------------------

[ IMAGE 36 — The employee notifications page ]

Same exact UI and concept as the manager notifications, with different contents.
Employees get notified when:

    - Their schedule changed. Shifts that were removed get tagged "Dropped Shift"
      rather than the generic "Shift Change," so it's obvious at a glance what
      happened
    - Somebody asks them to cover or swap — with Accept and Decline right on the

arriving as a pile of separate ones. The rule is time-based: anything affecting the
same person within a five-minute window merges into one.


==============================================================================
HOW A SHIFT REQUEST MOVES
==============================================================================

This is the part of the app with the most moving pieces, so it's worth laying out
on its own.


COVER AND SWAP: TWO STAGES

      Employee A              Employee B              Manager
          |                       |                      |
          |  asks B to cover ---->|                      |
          |                       |                      |
          |                 Accept or Decline            |
          |                       |                      |
          |<---- declined --------|  (ends here)         |
          |                       |                      |
          |                       +--- accepted -------->|
          |                                              |
          |                                    Approve or Deny
          |                                              |
          |<-------- schedule updated on approval -------+

The coworker gets asked first. They get a notification with Accept and Decline, and
only if they accept does the request move on to the manager, who then approves or
denies it. If they decline, the request ends right there — the manager never sees
it, and the person who asked is told.

That ordering is the whole point. It means nobody ends up on a shift they never
agreed to, and the manager's queue only ever contains requests where both employees
are already on board.

The schedule only changes when the manager approves. Both employee stages are just
agreements; the manager is what makes it real.

The app also remembers what was actually agreed to. The specific shift each person
signed off on is recorded when the request is made, so if the schedule moves
underneath a pending request — say the manager reschedules one of them in the
meantime — approving it won't silently trade away hours nobody agreed to. The
manager gets told the request no longer matches instead.


DROP REQUESTS: ONE STAGE

A drop request has no coworker to ask, so it goes straight to the manager. Has to
be at least two weeks out.

A FEW OTHER THINGS
==============================================================================


WHAT THE APP NOTIFIES ABOUT

    Schedule published with changes        each affected employee
    Shift removed                          that employee, tagged "Dropped Shift"
    Assigned to an event                   that employee
    Taken off an event, or event cancelled that employee
    Cover or swap request sent             the coworker being asked
    Coworker accepts                       the requester, and the manager
    Coworker declines                      the requester
    Request withdrawn                      whoever was waiting on it
    Manager approves or denies             both employees involved
    Drop request submitted                 the manager
    Availability submitted                 the manager


AUTOMATIC CHANGE NOTIFICATIONS

When a manager publishes a schedule, the system compares it against the previously
published version and notifies only the employees whose own shifts changed,
describing the actual difference:

    "Thu, Aug 13: moved to 9:00 AM – 2:00 PM (was 7:30 AM – 12:30 PM)"

    - Publishing a full week collapses into one notification per person, not seven
    - A first-time publish establishes the schedule rather than reporting a
      change, so it doesn't notify the whole roster about a week they're seeing
      for the first time
    - Approving a request doesn't double-notify — the approval message covers it


LIVE UPDATES

Notifications and pending requests refresh automatically — when the browser tab
regains focus, and on a background interval while the tab is visible. Updates
arrive without a page reload, preserving scroll position, open dialogs, and
in-progress work.


RULES THE APP ENFORCES

Collected in one place, since they're otherwise spread across the whole document.

    Availability            scheduling outside it warns, manager may override
    Weekly hour cap         per employee; going over raises a warning
    Minimum staffing        per day type; shortfalls listed by half-hour window
    Desk hours              Mon–Thu 9:00–6:00, Fri 9:00–5:45, Sun 1:00–6:00,
                            Sat closed
    Desk turn length        capped at one hour when auto-generated
    Desk overlap            two people on the desk at once is flagged
    Desk vs. events         being on the desk during an assigned event is flagged
    Event staffing          events below their required headcount are flagged
    Event coverage          a shift is stretched to cover an event the person is
                            assigned to
    Adjacent shifts         shifts that touch get merged into one
    Drop notice             at least two weeks ahead
    Cover/swap window       three weeks ahead
    Publishing              editing a published day returns it to draft
                            automatically
    Concurrent edits        two managers saving the same day — the second save is
                            rejected rather than overwriting the first


SECURITY

    - Passwords hashed with bcrypt; plaintext is never stored or logged

    - Sessions use signed tokens with a fixed expiry

    - Immediate revocation — removing an employee or resetting a password ends
      their active sessions right away, rather than leaving a valid session until
      it expires

    - Server-side authorization on every request; role and identity are read from
      the database, never trusted from the client

    - Scoped data access — employees can only read their own availability, only
      the requests they're actually part of, and only notifications addressed to
      them

    - Notifications can't be forged. Anything carrying an Approve or Deny button
      is written by the server, so nobody can send a notification under somebody
      else's name or attach one to a request they aren't part of

    - Forced password change on new accounts, enforced server-side

    - Rate-limited logins, per account, so one person's failed attempts can't
      lock out the team

    - Security headers via Helmet

    - Input validation on every write, with clear errors for invalid data

    - Destructive scripts refuse to run in production and require explicit
      confirmation before they'll touch anything


==============================================================================
RUNNING LOCALLY
==============================================================================

Requirements: Node.js 18+ and a MongoDB connection string.


BACKEND

    cd scheduling-app/src/backend
    npm install

    # create .env with:
    #   MONGODB_URI=
    #   JWT_SECRET=
    #   SLACK_ENABLED=false

    npm run seed -- --yes    # first run only — creates sample staff and accounts
    npm run dev              # http://localhost:3001


FRONTEND

In a second terminal, from the project root:

    cd scheduling-app
    npm install
    npm run dev              # http://localhost:5173


SCRIPTS

    npm run seed                  reports what it would destroy, then exits
                                  without writing anything

    npm run seed -- --yes         resets all staff and accounts from sample data

    npm run seed:users            creates login accounts for existing staff —
                                  safe to re-run, deletes nothing

    npm run seed:availability     populates sample availability

The seed script deliberately does nothing without --yes. It names the database it's
pointed at and counts what it would delete first, so it can't wipe real data because
somebody ran the wrong command in the wrong terminal. It refuses outright in
production.

NEXT STEPS
==============================================================================


SLACK INTEGRATION

The Slack groundwork is already in place — Bolt is installed and the backend
connects over Socket Mode as soon as a bot token, signing secret, and app token are
supplied, with the connection kept deliberately optional so a bad token can never
stop the API from serving.

What's missing is the bridge between the app and the workspace. The first step is
storing a Slack user ID alongside each staff record, which is what lets a
notification find a person. From there, the existing notification pipeline can
mirror anything addressed to an employee straight into a DM, so schedule changes and
cover requests reach people where they already are instead of waiting to be
discovered on the notifications page.

The natural follow-on is making those messages interactive — Accept and Decline
buttons on a cover request, Approve and Deny for the manager — so a shift can be
settled without anyone opening the app at all.

Worth noting for whoever picks this up: Socket Mode needs no public URL, which is
ideal for internal use, but a hosted deployment may be simpler to run in HTTP mode,
and slackClient.js documents the switch.


DEPLOYMENT

The app hasn't been deployed yet. Jetstream2 is the plan. The remaining work there
is standard — a public hostname, HTTPS, and pointing the frontend at the deployed
API instead of localhost.
